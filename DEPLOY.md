# Deploying to Render + Supabase

One Render web service runs the Spring Boot API **and** serves the React site, so everything is on one URL (for example `https://gndec-events.onrender.com`). The database is a Supabase project. Both sit in **Singapore**, so database calls stay fast.

```
Browser ──HTTPS──▶ Render (Docker: Spring Boot + built React site) ──▶ Supabase PostgreSQL (schema "scems")
```

The files that drive this are [Dockerfile](Dockerfile), [render.yaml](render.yaml) and the `prod` / `postgres` profiles in [application.yml](backend/src/main/resources/application.yml).

## 1. Push the code to GitHub

Render deploys from GitHub. Push this branch (or merge it into `main` first). Render builds whichever branch holds the `render.yaml` you create the Blueprint from.

## 2. Create the database (Supabase)

1. At supabase.com, create a project. Region: **Southeast Asia (Singapore)**. Pick a strong database password and keep it in a password manager.
2. Open the project, click **Connect**, and choose **Session pooler**. Don't use the "Direct connection" (IPv6 only on the free plan) or the "Transaction pooler" (it drops the session settings the app needs).
3. From the shown URI `postgresql://postgres.<ref>:[YOUR-PASSWORD]@<host>:5432/postgres`, note down:
   - `DB_URL` = `jdbc:postgresql://<host>:5432/postgres?sslmode=require`
   - `DB_USER` = `postgres.<ref>`
   - `DB_PASSWORD` = your database password

You don't create any tables. The app creates them in its own schema, `scems`, on first start. That schema is not exposed through Supabase's public REST API, so leave **Settings → API → Exposed schemas** as it is.

## 3. Create the web service (Render)

1. On render.com: **New → Blueprint**, connect the GitHub repository, and pick the branch.
2. Render reads `render.yaml` and asks for the values marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `DB_URL`, `DB_USER`, `DB_PASSWORD` | from step 2 |
   | `ADMIN_EMAIL` | the first administrator's email, e.g. `admin@gndec.ac.in` |
   | `ADMIN_PASSWORD` | a temporary password: 8+ characters with upper case, lower case and a number |

   `JWT_SECRET` and `PASS_KEY` are generated by Render. Never change `PASS_KEY` once students have passes: their QR codes are stored encrypted with it.
3. **Apply.** The first build takes several minutes (it builds the site, then the API). Watch the logs for
   `Created administrator ... from ADMIN_EMAIL`.

## 4. First sign-in

1. Open the service URL, choose **Faculty / Staff**, and sign in with `ADMIN_EMAIL` and the temporary password. You'll be asked to set your own password.
2. In Render → the service → **Environment**, delete `ADMIN_PASSWORD`. It is only read when no administrator exists.
3. Set up the college data. The production database starts empty apart from the departments:
   - **Control Panel → Venues & gates**: add venues and their entry gates.
   - **Control Panel → Student Import**: upload the student CSV, then download the temporary passwords.
   - **Control Panel → Users**: add organizers and security staff.

## 5. Before an event day

The free plan sleeps after 15 minutes without traffic and needs about a minute to wake. It also has 512 MB of memory and a tenth of a CPU. The app fits: it used about 360 MB in a rehearsal with the same limits.

- For demos, free is fine. The first visit after a quiet spell shows Render's loading page for about a minute.
- For a real event, don't let the gate scanner be the request that wakes the server. Either:
  - switch the service to a paid instance for the event period (more CPU also makes sign-in faster when many students log in at once), or
  - keep it awake with a free uptime monitor (for example UptimeRobot) calling `https://<your-service>.onrender.com/actuator/health` every 5–10 minutes. One always-on free service fits within Render's 750 free hours a month.
- Supabase free projects pause after a week with no activity. Open the dashboard and resume the project if the site reports database errors.

## Updating

Every push to the deployed branch redeploys automatically. Commits that only touch documentation are skipped (`buildFilter` in `render.yaml`). Database changes ship as new Flyway migrations, written for **both** `db/migration/mysql` and `db/migration/postgresql`.

## Custom domain

If you add one in Render (e.g. `events.gndec.ac.in`), also set `FRONTEND_ORIGIN=https://events.gndec.ac.in`. The API only accepts requests from the sites listed there; by default that is the service's own `onrender.com` URL.
